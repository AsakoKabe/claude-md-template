## Правила поведения

### 1. Думай до кода
- Допущения называй вслух. Не уверен — спроси.
- Расходятся два прочтения — покажи оба, а не выбирай молча.
- Есть путь проще — скажи. Возражай, когда есть чему.

### 2. Сначала простота
- Ничего сверх просьбы. Никаких абстракций ради одного места использования.
- Никакой обработки невозможных сценариев.
- Если 200 строк можно сделать 50 — переписать.

### 3. Точечные правки
- Не «улучшай» соседнее: ни код, ни комментарии, ни форматирование. Повторяй форму соседнего кода.
- Удаляй только то, что сделали неиспользуемым твои правки.
- Каждая изменённая строка отслеживается до задачи.

### 4. Цель и проверка
- Задача превращается в проверяемую цель с критерием готовности.
- Для многошаговой задачи — короткий план: `[Шаг] → проверка: [чем]`.
- Перед новой фичей подтверди план; после кода — self-review; перед коммитом — гейты.

## Правила работы
- **Docs-sync**: структурное изменение (модуль, слой, паттерн) — в этом файле тем же коммитом; подробность, видная в коде, сюда не переносится
- **Коммиты**: conventional commits, тема <на языке проекта>. **Никогда `git add -A`** — явный список путей; `--amend` — с тем же списком или при пустом индексе
- **Как писать**: докстринг — одна-две строки; комментарий — только ограничение, которого код не показывает. Код, комментарии, тесты, UI — <язык>. <Линтер и длина строки>, <проверка типов>
- **Тесты**: сначала прочитать модуль и его тесты. **Сначала падающий тест** — красный до правки, сказать в отчёте. Проверять неразличимость, которой быть не должно, а не наличие поля. Правило — тестом того модуля, где оно живёт
- **Отчёт**: изменённые файлы, команды, результат, известные ограничения
